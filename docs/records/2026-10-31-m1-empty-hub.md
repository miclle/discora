# 2026-10-31：USB-OTG 桥接后的空 Hub 枚举

结论：**空 Hub 在 ESP32-S3 上成功以 Full-Speed 枚举（bench-tested）。** 尚未接回光驱和辅助供电，未执行光驱 INQUIRY、TUR 或 sense。

## 条件与证据

- 用户按前述桥接步骤复测，报告 `USB-OTG` 焊盘 A、B 对 GND 均为 **4.83 V**，当时只连接 COM，USB 口没有其它连接。焊盘电压为用户测量，不是自动采集。
- 仅打开 Discora 的目标 COM（USB Single Serial），没有打开其它项目的原生 USB 串口。串口采集代码未主动发出复位脉冲；打开端口后捕获到一次启动日志，不能据此把它记作真实断电冷启动。
- 用户随后确认空 Hub 上行已接到开发板 USB；Hub 下游全部拔空，光驱与充电宝断开。
- 固件仍为 v5.4 / `61b8229-dirty`，ELF SHA-256 `2a1a3d89bba7655f05edd8c508119a9fbad5a57394fd5a78b3096d44f2bfcb90`，没有为本次实验重新烧录或修改代码。

## 真实串口摘录

```text
I (15265) usb_probe: USB address=1 VID:PID=05e3:0610 speed=Full-Speed config=1 device_class=0x09
I (15265) usb_probe: interface=0 alt=0 class=0x09 subclass=0x00 protocol=0x00
W (15275) usb_probe: no supported Full-Speed BOT interface (hub/UAS/other/malformed); skipped
I (15275) usb_probe: device closed; free internal heap=369092
```

class `0x09` 是 Hub。M1 的 BOT client 跳过 Hub 接口是预期行为，不代表 Hub 枚举失败；底层 IDF Hub 驱动处理下游端口。日志中的 device closed 是探测 client 释放自身打开的 Hub handle，不是让 Hub 断电。

整个串口采集窗口为 180 秒，未观察到 panic、abort、brownout 或第二次启动记录。这不是长时稳定性、下游设备兼容性或带载供电验收。

原始日志当时存放于被忽略的 `firmware/build/bench-2026-10-31-9k2eyvtm/uart-empty-hub-195934.log`，3,813 字节，SHA-256 为 `d60c04c5897352d93e6bea43560072c785189123c5271290eda7c4a2b2f0d9dd`。首次未枚举记录继续保留在 [首次上板记录](2026-10-31-m1-first-boot.md)，不能用本次成功覆盖此前失败条件。

## 下一步

光驱适配器为双 USB-A 分叉供电线。接回充电宝前，先在完全断电状态确认两插头 5V 是否直连、是否存在隔离；USB-OTG 桥接改变了 VBUS 与板上 5V 的连接关系。不要把空 Hub 枚举成功当作批准未知双电源并联的依据。

供电路径确认后，再接光驱进行真实 BOT / INQUIRY / 介质查询；尚未开始 M2 CD-DA。
